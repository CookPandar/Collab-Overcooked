# 奖励梳理与 reward shaping 方案（2026-10-28）

本文梳理 L2 think RL 实验（`l2r_*`、`l2t_*`）用到的所有奖励项，给出数值和实测量级，分析冗余通信的成因，并给出重新设计的方案和已实现的代码改动。

代码位置：

- `baselines/rl/credit.py`：逐次调用的环境奖励；
- `baselines/rl/advantages.py`：优势计算；
- `baselines/rl/train.py`：思考奖励的合成；
- `baselines/rl/rule_rewards.py`：规则思考奖励。

## 1. 现有奖励一览

### 1.1 环境奖励（每次 LLM 调用一个 reward）

| 项 | 数值 | 触发条件 | 实测（l2r_none u20–25，4007 次调用） |
|---|---|---|---|
| format | −0.2 | 输出格式错误 | 1% 的调用 |
| validator | −0.1 | 厨房动作被环境拒绝 | 8% 的调用 |
| ITES | ΔTES × 1.0 | 厨房动作执行后，TES（与参考解的 F-β 匹配，β=0.95）的变化量；**消息和 wait 不计入动作历史** | 8% 的调用非零，非零时平均 +0.08，范围 [−0.09, +0.32]；每个角色每局累计最多 1 |
| terminal | +2.0 | 送餐成功，加在每个角色最后一次调用上，再按时间步折扣（γ=0.99）分给前面的调用 | 成功局每个角色一次 |
| collab | `collab_weight` × 承诺增益 | 消息请求的动作能让队友 TES 增加时，**发送时就给**；队友执行时也给 | 未启用（0） |
| uncoop | `uncoop_penalty` | 重复消息（repeat）；可做却在等待（idle） | 未启用（0） |
| redundancy | `redundancy_penalty` | 重复的 Collab 消息；Chef 拿着生食材时等待或说话 | 未启用（0） |

### 1.2 优势计算

所有 `l2r_*` / `l2t_*` 都用 `advantage_estimator: reinforce`、`advantage_norm: null`：

A = 本次调用的局部奖励 + keep × Σ_{t′≥t} γ^(t′−t) × terminal，A 截断在 ±10。

- format 或 validator 出错、或被标为 uncooperative 的调用，keep=0，分不到成功奖励。
- **没有基线，也不做归一化。** 代码里有按角色归一化（`advantage_norm: role` / `role_sign`），但这批实验都没开。
- **折扣只按时间步算**：同一时间步内的多次调用拿到相同的成功份额。

### 1.3 思考奖励（只在 `l2r_*` / `l2t_*` 中）

| 项 | 范围 | 含义 |
|---|---|---|
| ground | [−2, 1] | 第一视角：自己和厨房的状态说得对不对、全不全 |
| mate / mate_v2 | [−1, 1] | 队友信度：对队友状态和意图的判断、发出的请求是否合理且被执行 |
| plan | 约 [−1, 1] | 长程规划：Recent Goal 和参考解剩余步骤的匹配程度 |
| full | [−4, 3] | 三项直接相加，没有归一化 |
| LLM 评委（`l2t_*`） | 0–1，另加 grounded 分 | 评委 prompt 里写了动作有没有推进参考进度 |

**合成方式：**

1. 按角色在 batch 内中心化，记为 j；
2. `scale: match`：乘以 max(1, std(A)/std(j))；
3. 乘 weight=1。

**作用位置（mode）：**

- **sum**：A + w·j 加在这次调用的**全部** token 上，包括 Action；
- **split**：推理 token（Think + Recent Goal）拿 A + w·j，**Action token 只拿 A**。

## 2. 实测：消息的优势严格高于厨房动作

各类调用拿到的动作优势（rollout u20–25）：

| | 成功局：动作 | 成功局：消息 | 成功局：wait | 失败局：动作 | 失败局：消息 | 失败局：wait |
|---|---|---|---|---|---|---|
| none：平均 A | +0.97 | **+1.61** | +1.65 | −0.03 | **0.00** | 0.00 |
| none：A>0 的比例 | 56% | **100%** | 100% | 17% | 0% | 0% |
| full：平均 A | +1.15 | **+1.67** | +1.44 | −0.13 | 0.00 | −0.41 |

思考奖励的量级：full 的思考项 std=0.89，范围 [−4.8, +2.5]，与 A（std 0.72–1.26）同样大。

冗余通信的程度：

| 实验 | 重复消息占比（自上次执行动作以来已发过） | 每角色每步调用 1 次的比例 | 每角色每步调用 7 次的比例 |
|---|---|---|---|
| none u24 / u46 | 0.26 / 0.23 | 0.34 / 0.41 | 0.01 / 0.02 |
| full u38 | **0.79** | 0.14 | **0.38** |
| LLM 评委 sum u46（成功率 0.75） | 0.07 | 0.60（另有 35% 是 2 次） | 0 |

## 3. 冗余通信的成因

1. **消息零风险。** 消息不会被拒，也不进 TES 历史。在成功局里它总能分到约 +1.6 的成功份额，在失败局里恰好是 0。厨房动作被拒时，实际损失约 1.7：罚 0.1，再失去约 1.6 的成功份额。**在期望上，发消息严格优于做动作。**
2. **同一时间步内多发不吃亏。** 折扣只按时间步算，发 1 条和发 8 条，每条拿到的份额一样。
3. **没有基线。** 失败局里的废话 A=0，从不受罚；成功局里的废话全部被强化。
4. **规则思考奖励放大了偏差。** `match` 把它放大到与 A 同样大，而且它对不同动作类型不中性：
   - plan 下做动作平均 −0.17，消息 +0.03；
   - full 下 wait 平均 −0.23 到 −0.30。
   - 结果模型被推向发消息：full 组 Assistant 做动作的比例从 0.60 降到 0.11。
5. **LLM 评委组没有这个问题。** 评委看得到动作结果，会压低没用的消息（消息平均 −0.05 到 −0.15），等于给了一个逐次调用的结果奖励。

## 4. 新增的机制（已实现，默认关闭，不影响正在跑的实验）

### 4.1 时间步内折扣 `intra_gamma`（`advantages.compute_advantages`，`train.py`）

- 同一角色在同一时间步内的第 k 次调用（k=0,1,2…，按 call_index 排序），成功份额乘以 intra_gamma^k。
- 折扣在每个时间步开头重置，**不影响前面时间步的调用**；时间步之间仍按 γ=0.99 折扣。
- 局部奖励（ITES、惩罚）不打折。
- 例：一步内调用 3 次，intra_gamma=0.5 时，份额依次为 1、0.5、0.25。
- 配合按角色归一化后，多出来的轮次会拿到低于均值、也就是负的优势，从而鼓励用更少的轮次完成沟通。
- 默认 1.0 等于关闭；建议值 0.5。
- 之前要求过这个机制，但当前训练代码（`baselines/rl`）里没有实现，所以已有实验都没用上。现已补上。

### 4.2 重复消息惩罚（`credit.CallCredit`，`uncoop_penalty` + `uncoop_kinds`）

- **判定改为：** 自上次有动作执行以来（任一角色执行都算），同一角色已经发过相同内容。
  - 旧定义只比较上一条，A、B、A、B 交替发就能绕过。
- **被判重复的消息：** 罚 −`uncoop_penalty`，并且失去成功份额（keep=0），与无效动作同等对待。
- **`uncoop_kinds`：** 选择惩罚哪几类。`["repeat"]` 只罚重复消息；`["repeat", "idle"]` 同时罚"可做却等待"。
- **建议配置：** `reward: {..., uncoop_penalty: 0.1, uncoop_kinds: [repeat]}`。
- **按新定义回看已有 rollout，会被罚的消息比例：** none 约 23–26%，full u38 约 79%，LLM 评委 sum 约 7%。

### 4.3 优势基线（已有，打开即可）

`advantage_norm: role`：按角色在 batch 内减均值、除标准差，失败局的调用会拿到负优势。

`role_sign` 是保号版本：原来为正的仍为正，原来 ≤0 的仍 ≤0。它不能让失败局里 A=0 的废话变成负值，所以这里要用 `role`。

### 4.4 消息采纳奖励 `reward.collab_mode: uptake`（`credit.CallCredit`，10-28 实现）

- 配置：`reward: {..., collab_mode: uptake, collab_weight: 0.5, collab_window: 5}`。
- 发送 Collab 请求时**不给分**，只登记（请求的动作、截止时间步 = 发送时间步 + `collab_window`）。
- 队友在截止前执行了被请求的动作、且该动作 ITES > 0 时，发出请求的那次调用得到 `collab_weight` × 这次实际的 ITES 增益。
- 每个请求最多兑现一次；同一发送者对同一动作的请求还没兑现时再发一遍，不再登记（重复请求拿不到分）。多条请求指向同一动作时只兑现最早的那条。
- 队友本身除 ITES 外不额外加分。
- 不设 `collab_mode`（默认 `promise`）时，行为与原实现完全相同（发送时按承诺增益给分）。
- 每轮指标 `comm/uptake_rate` = 被采纳的请求数 / 新请求数。

### 4.5 思考奖励改造（`think_reward` 的新选项，10-28 实现）

- `rules_combine: mean`：启用的规则奖励按权重取平均（full_v2 约在 [−1, 1]），默认 `sum` 不变。
- `scale: ratio`，`ratio: 0.25`：每个 batch、每个角色，把中心化后的思考信号缩放到 std = 0.25 × std(A)（A 为该角色的动作优势）。
- `center: role_type`：在 (角色, 动作类型) 组内中心化，类型为消息 / wait / 厨房动作 / 其他（格式错误等），用 `response_mode` 判定；默认 `role` 不变。这样思考项在每类动作内均值为 0，无法改变"选哪类动作"的偏好。
- 只配 split 使用。

### 4.6 每轮通信指标（`train.py` 的 metrics.jsonl，10-28 起的新实验都有）

`comm/repeat_share`（重复消息 / 全部消息，定义同 4.2，不论是否开惩罚都统计）、`comm/calls_per_agent_step`、
`comm/{msg,wait,action}_share_{chef,assistant}`、`comm/uptake_rate`。rollout 里也新增 `repeat`、`collab_requests`、`uptaken` 字段。

## 5. shaping 方案

原则：

1. 以 terminal=2 为单位，各项量级要可解释；
2. 消息、wait 和动作都按"对任务的实际作用"记分；
3. 思考奖励是辅助信号，不能盖过环境信号。

| 项 | 现在 | 建议 |
|---|---|---|
| terminal | +2.0 | 不变 |
| ITES | ×1.0 | 不变 |
| format / validator | −0.2 / −0.1，并失去成功份额 | 不变 |
| 时间步内折扣 | 无 | `intra_gamma: 0.5` |
| 重复消息 | 0 | −0.1，并失去成功份额 |
| idle（可做却等待） | 0 | 先不加；S0 之后看 wait 的比例再决定 |
| 消息被采纳 | 未启用，且现有实现是发送时就给 | 改成队友 5 步内执行了被请求的动作才给，0.5 × 该动作的 ITES 增益（待实现） |
| 优势基线 | 无 | `advantage_norm: role` |
| 思考奖励总量 | 三项相加，`match` | 三项取平均（约 [−1, 1]）；固定缩放，让思考项 std ≈ 0.25 × std(A)（待实现） |
| 思考奖励中心化 | 按角色 | 按角色 × 动作类型（消息、wait、动作分别中心化），使它无法改变"选哪类动作"的偏好（待实现） |
| 思考奖励作用位置 | sum 或 split | 只用 split |

## 6. 验证计划

都在 L2 上跑 50 轮，只用 3 道训练菜，与已有的 l2r_none 对照。

| 组 | 配置 | 要回答的问题 |
|---|---|---|
| S0 | none + `intra_gamma 0.5` + 重复消息 −0.1 + `advantage_norm role` | 冗余通信能否压下来，中期是否还下滑 |
| S0a | none + `advantage_norm role` | 单独的基线贡献多少 |
| S0b | none + 按条消息收费 −0.05（待实现） | 粗惩罚的对照 |
| S1 | S0 + 消息采纳奖励 | 有用消息的正向信用 |
| S2 | S1 + 改造后的思考奖励（full_v2：取平均、按动作类型中心化、固定缩放、split） | 在干净的结构上，思考奖励是否还有增益 |

**指标：**

- 成功率：训练，以及评测（L2 分训练菜和 held-out）；
- 每局调用数、每角色每步调用数、重复消息占比；
- 各角色动作、消息、wait 的比例；
- 被采纳消息的比例。

**成本：** S0、S0a、S0b、S1 不调用评委，只占 GPU，每组约 10 小时（l2r_none 用时）；S2 的 API 用量与现在的 full_v2 相同。
