# 奖励问题诊断与团队进展回报（2026-11-03）

本文接在 `docs/reward_shaping.md` 之后。

**起因**：L2 上的 PPO 和 GRPO 基线（`l2g_grpo_faithful`、`l2g_drgrpo_fix`、`l2g_gigpo_fix`、`l2p_ppo_fix`）全部失败，表现为学不动或中途崩溃。

**本文做了三件事**：
1. 用已保存的 rollout 把奖励的问题逐条定位清楚；
2. 给出新的奖励机制"团队进展回报"（`reward_scheme: team`）；
3. 用离线检验选定参数。

**脚本与输出**：`/archive/public/zhangshuwen/reward_redesign_20261103/`
- `analyze.py`：类别统计；
- `trace.py`：逐步轨迹；
- `offline_gate.py`、`grid.py`：离线检验；
- `request_test.py`：请求对错检验。

坍塌机制的子任务报告在 `/archive/public/zhangshuwen/framework_audit_20261102/collapse_20261103/`。

## 1. 任务本身

L2 训练菜共三道：烤南瓜片、煮四季豆片、煮土豆片。每道菜每个角色只有一条 5 步参考解。以烤南瓜片为例：

- **Assistant**：取南瓜 → 放上砧板 → 切 → 取南瓜片 → 放到柜台
- **Chef**：从柜台取南瓜片 → 放进烤箱 → 烤 → 取出 → 上菜

Chef 够不到食材分发器，所以必须等 Assistant 把切好的南瓜片放上柜台。合起来，全队只有 10 步。

## 2. 奖励有什么问题（证据）

### 2.1 消息零风险，而且大多数调用都是消息

在 l2r_none 的全部 50 轮里，**67% 的调用是 Collab 消息**（Chef 35%，Assistant 32%），wait 占 14%，厨房动作只有约 18%。

| 调用类型 | 即时奖励 | 说明 |
|---|---|---|
| 消息、wait | 恒为 0 | `credit.py:467` 直接返回 |
| 厨房动作 | 被拒 −0.1；偏离参考 ITES < 0 | |

ITES 来自 TES，即 F-β 匹配，分母里含有 `len(history)`。所以**每多做一个不在参考上的合法动作，TES 就会下降**，而消息不进动作历史。

结论：只有"动手"有成本，"说话"永远没有。

### 2.2 消息的好坏完全没有被奖励区分：Chef 的错误指令反而被强化

失败局的典型过程（`trace.py`，l2r_none u1 第 3 局）：
- Chef 一再要求 Assistant "把南瓜放到柜台上"（还没切），又要求它"从分发器再取一个"；
- Assistant 照做，一直在搬东西；
- 第 18 步 Assistant 才把南瓜放上砧板；
- 最终 Chef 一步参考进度都没有。

失败局的最终参考深度（Chef, Assistant），出现最多的几种：

| 深度 | 局数 | 含义 |
|---|---|---|
| (0, 2) | 37 | 放上砧板但没切 |
| (0, 3) | 35 | 切了但没取 |
| (0, 5) | 23 | 都放上柜台了，Chef 却一直没去取 |

**用参考解来判断请求的对错**：如果请求的动作正是对方下一步的参考动作，记为"对"，否则记为"错"。

| | Chef 对的请求 | Chef 错的请求 |
|---|---|---|
| l2r_none 数量 | 845 | **7936（90%）** |
| 旧奖励下的平均优势（reinforce，无基线） | +0.29 | **+0.16** |
| LLM 评委 sum 组的评委分 | 0.74 | 0.43 |
| 新机制（见第 3 节）的平均优势 | **+0.04**（评委组 +0.07） | **−0.005**（评委组 −0.009） |

**旧奖励下，错误请求的优势平均为正，它们一直在被强化。** 原因有两条：
- 消息的局部奖励恒为 0；
- 成功局里所有调用都分到成功奖励。

一条消息好不好，取决于它让队友接下来做成了什么。而现有奖励只按个人的动作历史给分（ITES 只看自己），队友的进展从来不会回到发消息的人身上。

### 2.3 结果奖励稀疏

l2r_none 的训练成功率是 0.19。按"同一轮、同一道菜"分组，**115/150 组全部失败**。

GRPO 只比较组内的结果分。全败组里只剩下零星的 −0.1、−0.2 罚分和 ITES 可比，信号极弱。

### 2.4 估计器把上面的偏差放大（子任务报告）

- **GRPO（faithful）**：一局所有调用共享同一个分数，分数又是罚分之和，然后除以组内标准差。
  - 后期每局有一百多个格式错误，少错一两个的那局就拿到 +1σ。
  - u50 有 45% 的格式错误调用拿到正优势。
  - `gates: [invalid]` 只把它截成 0，不会变成负值。
- **按角色白化**（PPO，以及 S0 的 `advantage_norm: role`）：全败的 batch 里标准差很小，−0.1 的拒绝被放大到 −1σ 到 −2σ，而消息恒在 0 附近，"只说话不动手"成了最安全的选择。
  - faithful 在 u25：Chef 推进最多的一局拿到 A=−1.41，完全不动手的一局拿到 +0.37。
  - Chef 进入"所有局都得 0、组内无差异、没有梯度"的吸收态。
- **空回复不罚**：没有 `Action:` 的回复（多数是截断在 384 token）不扣分；格式纠正重试里的 missing_action 也不上报。faithful u50 有 136 个这样的调用。

### 2.5 优化：漂移不受控

- 参考 KL 系数 0.02，比策略梯度项小两个数量级。kl_guard 的阈值是 1.0，在四个 run 里一次都没触发。
- agentgym 目标按每 16 个调用切 minibatch，不打乱。
  - 每轮的优化步数随调用数增长：faithful 从 31 增到 142，drgrpo/gigpo 最多到 299。
  - 同一个 minibatch 是同一局的连续调用。
- 格式错误会触发纠正调用，调用数随之增加，优化步数也增加，形成正反馈。
- 这一条只有相关性证据（KL 与累计步数），离线无法验证。

## 3. 新机制：团队进展回报（`reward_scheme: team`）

原则：
- 每类调用都用同一把尺子打分，即**它之后全队有没有进展**；
- 只用环境可验证的事实：参考进度、是否送达、格式是否合法、动作是否被环境拒绝；
- 不按调用类别给固定分，因为 S4 已经证明这会被钻空子。

### 3.1 奖励

1. **团队进度** Φ ∈ [0, 1]：两个角色已执行的合法厨房动作在各自参考解上的顺序匹配深度之和，除以两条参考解的总长（`advantages.team_progress`）。
   - Φ 只增不减，全局上限为 1。
   - 来回拿起放下不会增加 Φ，所以刷不出分。
   - 不再使用 F-β 形式的 TES，因此合法但偏离参考的动作不会被扣分。
2. **团队奖励**：第 t 步 R_t = ΔΦ_t，送达那一步再加 1。两个角色共享。
3. **团队回报**：G_t = Σ_{t'≥t} γ^{t'−t} R_{t'}，γ = 0.7（按时间步计）。
   - 一条消息如果让队友在接下来几步里做成了参考动作，就能分到这份进展。
   - 1/(1−γ) ≈ 3 步，大致对应"请求、对方执行"的时间。
4. **局部项**：只记在本次调用上，不进入回报。
   - **非法输出 −0.5**：格式错误、mixed、malformed，以及没有 Action 的空回复（`reward.empty_invalid: true`）。
   - **被环境拒绝的动作 −0.2**。
   - **每次调用 −0.01**：对所有类型一样，是"带宽成本"。
   - 非法输出的优势强制为 min(A, 0) + 罚分 < 0，永远不会被强化。

### 3.2 优势

| 估计器 | 配置 | 优势 |
|---|---|---|
| GRPO 式（组相对、按时间对齐） | `advantage_estimator: team`，`team.baseline: group_time` | A = G_t − 同组（同一道菜、同一轮的另外 3 局）在同一时间步的平均团队回报（留一法；已结束的局记 0）+ 局部项 |
| REINFORCE | `team.baseline: batch` | 基线为本轮该角色所有调用的平均团队回报 |
| PPO | `advantage_estimator: gae` + `reward_scheme: team` | 团队奖励落在每个角色在该时间步的最后一次调用上；critic 学团队回报；GAE γ=0.85（每个时间步约 2 次调用，约合每步 0.7）、λ=0.95；局部项不进回报（`local_penalties`）；`std_floor: 1.0`；`gates: [format]` |

三种都**不除以组内标准差**，所以小差异不会被放大。

### 3.3 优化

- **`update_steps: 16`**：每个角色每轮固定 16 个优化步，调用先打乱再均分（`update._optimizer_steps`）。
  - 原先每 16 个调用切一个 minibatch，faithful 的优化步数从 31 涨到 299。改后固定为 32（两个角色合计），相当于原先起步时的水平，之后不再随调用数增长。
  - smoke 时试过每个角色 4 步：梯度范数只有 0.05，学得太慢，所以改为 16。
- **`kl_coef: 0.05`**。
- **`kl_guard.max_ref_kl: 0.2`**：超过就撤销这一轮的更新，并把学习率减半。

## 4. 离线检验与参数选择

**数据**：LLM 评委 sum 组（l2t_sum_matchfloor_g1，评测 0.87）的 50 轮 rollout，共 17,603 次调用。

**检验方法**：用新机制重算每次调用的优势，与评委的逐调用分数求相关系数。评委是目前唯一被证明有效的逐调用信用，用它作参照。

**参照基线**：旧环境奖励（reinforce，无评委项）与评委分的相关系数为：
- 全部调用 0.31；
- 失败组 0.38；
- Chef 消息 0.21。

`grid.py` 对 γ、拒绝罚分、基线做了网格搜索。

**塑形方式**：
- 先试的是严格的势函数塑形 γΦ′ − Φ：每个没有进展的时间步都会产生持有成本 (1−γ)Φ，在 γ ≤ 0.9 时会把推进动作压成负值，因此放弃；
- 改用进度增量（`shaping: delta`）。

部分结果（γ=0.7，按时间对齐基线）：

| 拒绝罚分 | 全部调用 | 失败组 | Chef 消息 | 动作 | 失败组各类平均 A（推进 / 合法未推进 / 被拒 / 消息 / wait / 非法） |
|---|---|---|---|---|---|
| 0 | 0.17 | 0.10 | 0.16 | 0.25 | +0.09 / 0.00 / +0.01 / +0.01 / 0.00 / −0.52 |
| 0.1 | 0.23 | 0.28 | 0.16 | 0.40 | +0.09 / 0.00 / −0.09 / +0.01 / 0.00 / −0.52 |
| 0.3 | 0.33 | 0.38 | 0.16 | 0.58 | +0.09 / 0.00 / −0.29 / +0.01 / 0.00 / −0.52 |

**选定的参数**：γ=0.7、拒绝罚分 0.2（介于两档之间）。

**选择理由**：
- 各类平均优势的排序与评委一致：推进 > 合法未推进 ≈ 消息 ≈ wait > 被拒 > 非法。
- 消息与动作之间没有系统性偏向，这与旧机制的两个失败方向都不同：旧机制下消息稳赚，S0 里动作被放大惩罚。
- 非法输出 100% 为负。

**局限**：
- 新机制与评委的相关性和旧环境奖励相当，不更高。Chef 消息的相关性（0.16）略低于旧奖励（0.21）。
- 环境事实只能捕捉"之后有没有进展"，判断不了"这句话说得对不对"。后者仍是 LLM 评委那 65% 的类别内信息（`reward_shaping.md` §8）。

**为什么仍要换掉旧奖励**：它在三处有系统性偏差，新机制都消除了：
1. 错误请求的期望优势为正（§2.2）；
2. 非法输出可能拿到正优势；
3. 经过标准差归一化后，"不动手"成了最优策略。

### 3.4 奖励单位

实跑时，第 3.1 节里的各项数值全部乘 2，与旧的终止奖励 2 对齐：
- 进度：满分 2；
- 送达：+2；
- 非法输出：−1；
- 被拒动作：−0.4；
- 每次调用：−0.02。

原因：没有标准差归一化时，奖励的绝对尺度直接决定步长。smoke 里乘 1 时梯度范数只有 0.05，而旧 run 约为 0.6。

各项之间的比例不变，所以第 4 节的离线检验结论仍然适用。离线检验本身用的是乘 1 的数值。
